# Rust #164250 host-compiler hardening record

## Scope and authority

This record concerns the Rust compiler used to build Bowfin. It changes no Bowfin
source-language semantics, accepted BD, frozen BED-038 composite, N1 plan or
replay authority, production gate, or evidence result. It does not accept any
BED-038 checkpoint. Human-only merge authority remains unchanged.

Upstream references:

- issue: [rust-lang/rust#164250 — struct's lifetime requirements can be bypassed
  via covariant field assignment](https://github.com/rust-lang/rust/issues/164250);
- proposed repair: [rust-lang/rust#164277 — require MIR local types to be
  well-formed](https://github.com/rust-lang/rust/pull/164277).

The issue was open and labeled `I-unsound`, `P-high`, `A-borrow-checker`,
`A-lifetimes`, `A-variance`, and `T-types` when rechecked on 2026-11-16. The
proposed repair was open and unmerged. Those upstream labels and states are
historical observations; current status must be rechecked before a toolchain
change.

## Bowfin exposure model

The reported compiler behavior permits a local aggregate type with declared
well-formedness requirements to be inferred from an unconstraining initializer
and later unified with a value that does not satisfy those requirements. The
original reproducer uses direct field assignment and a destructor to turn the
typing error into memory unsafety. Upstream repair controls also cover no-`Drop`
and array-unification cases. Bowfin therefore protects the declaration class,
not only the original exploit text.

The protected class is every Rust `struct`, `enum`, or `union` with a bound in
its generic parameter list or `where` clause. The `prod` baseline for this change,
commit `ac0382ea2299388a3557839316a8feeeed6d6990`, contains no such declaration
in tracked Rust source according to the repository-owned guard. That result is a
bounded source observation, not Arnold's independent BED-038 checkpoint audit and
not proof that rustc has no other soundness defect.

The active BED-038 Stage N1 investigation remains separate. Its exact checkpoint,
all generated or retained source, and every audit conclusion must be reconciled
before that work can rely on this record. Sarah's independent review remains
required before either the audit conclusion or this hardening change is treated
as confirmed.

## Preventive invariant

The canonical rule is TC-001 in `docs/ai/TOOLCHAIN_CONSTRAINTS.md`.

The default policy is deliberately stronger than the known exploit: bound-bearing
generic aggregate declarations are prohibited. A future exception must be exact,
reviewed, construction-closed, and covered by focused controls. This architecture
prevents a later field assignment, array unification, swap, replacement, or other
inference path from becoming the first place the type's declared requirements are
relied upon.

The invariant does not prohibit:

- ordinary lifetime-parameterized aggregates without bounds;
- unbounded generic aggregates;
- `const N: usize` generic parameters, whose colon supplies the const parameter's
  type rather than a generic bound;
- generic functions or implementations whose signatures establish their bounds
  directly;
- compile-only defect probes and adversarial scanner fixtures, which are isolated
  from production source and never executed.

## Mechanical controls

### Source guard

`scripts/verify-rustc-164250.py`:

- enumerates tracked `.rs` files using Git;
- excludes only the named probe and adversarial-fixture directories;
- tokenizes code independently of rustc;
- handles nested block comments, line comments, strings, raw strings, byte/char
  literals, lifetime tokens, generic nesting, tuple fields, and trailing `where`
  clauses;
- detects bound-bearing structs, enums, unions, and macro-contained declaration
  tokens;
- binds every exception to the declaration's normalized-token SHA-256;
- rejects unreviewed declarations and stale allowlist entries.

The empty initial allowlist is
`tools/rustc-164250/allowlist.json`. Adding an entry is a reviewed policy change,
not a routine lint suppression.

### Guard controls

`scripts/tests/test_verify_rustc_164250.py` covers:

1. direct `'static` bounds;
2. trailing `where` bounds on tuple structs;
3. the upstream array-unification shape with trait bounds;
4. lifetime-parameter bounds;
5. lawful const-parameter type annotations;
6. lawful unbounded generic aggregates;
7. comments, ordinary strings, raw strings, and nested block comments;
8. macro-contained declarations;
9. an exact reviewed allowlist entry; and
10. invalidation after declaration-digest drift.

The checked-in Rust fixtures make the rejected and permitted forms inspectable.

### Compiler-status probe

`scripts/probe-rustc-164250.py` compiles probe crates as metadata in a temporary
directory. It never executes them. With the repository's Rust 1.80.0 pin:

- `issue_164250.rs` is expected to compile, recording that the selected compiler
  exhibits the affected behavior;
- `explicit_type_control.rs` is expected to fail because the explicit
  `&'static` type makes the unsatisfied lifetime visible to borrow checking.

The status probe is intentionally separate from the source guard. Observing the
bug does not authorize vulnerable source; observing a future fix does not
silently change project policy.

### Continuous integration

The tests workflow runs the source guard, all scanner controls, and the compiler
probe for every push and pull request. The docs workflow independently verifies
that TC-001 remains in the generated AI context bundle. The checks apply before
any future N1 source can be accepted or merged.

## Maintenance and retirement

When upstream provides a candidate fixed release:

1. verify the upstream issue, repair, release notes, and exact compiler identity;
2. change the pinned toolchain only in a dedicated reviewed update;
3. invert the status probe from `affected` to `fixed`;
4. require the original and variant probes to fail compilation for the intended
   lifetime/WF reason rather than an unrelated host error;
5. run complete debug, release, Clippy, rustfmt, documentation, installation,
   native, and BED-specific gates applicable at that time;
6. reconcile any newly rejected code as a possible true positive before repair;
7. obtain independent review and Greg's explicit disposition;
8. retain the source guard unless that disposition expressly narrows or retires it.

No agent may infer retirement from a green compiler build, a changed diagnostic,
an upstream merge, a matching digest, or the absence of a current exploit.
