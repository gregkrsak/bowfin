## Bowfin exposure model

The reported compiler behavior permits a local aggregate type with declared
well-formedness requirements to be inferred from an unconstraining initializer
and later unified with a value that does not satisfy those requirements. The
original reproducer uses direct field assignment and a destructor to turn the
typing error into memory unsafety. Upstream repair controls also cover no-`Drop`
and array-unification cases. Bowfin therefore protects the declaration class,
not only the original exploit text.

The protected class is every Rust `struct`, `enum`, or `union` with a bound in
its generic parameter list or `where` clause. This rule is broader than
demonstrated affected code.

## Preventive invariant

The canonical rule is TC-001 in `docs/ai/TOOLCHAIN_CONSTRAINTS.md`.

The default policy is deliberately stronger than the known exploit: bound-bearing
generic aggregate declarations are prohibited. A future exception must be exact,
reviewed, construction-closed, and covered by focused controls. This architecture
prevents a later field assignment, array unification, swap, replacement, or other
inference path from becoming the first place the type's declared requirements are
relied upon.

The invariant does not prohibit:

- ordinary lifetime-parameterized aggregates without bounds;
- unbounded generic aggregates;
- `const N: usize` generic parameters, whose colon supplies the const parameter's
  type rather than a generic bound;
- generic functions or implementations whose signatures establish their bounds
  directly;
- compile-only defect probes and adversarial scanner fixtures, which are isolated
  from production source and never executed.

## Mechanical controls

### Source guard

**B124-01.** The default scan examines every tracked `.rs` file except the
isolated scanner fixtures and probe crates. It visits raw identifiers, macro
transcriber declarations, and nested items, including those within aggregate
declarations and const expressions. A Rust-splicing input must resolve from one literal relative path to a tracked,
nonexcluded regular `.rs` file already in the scan, without traversing symlinks.
Computed inputs, ambiguous macro contexts, and unresolved `#[path]` bases
require review. `include_str!` and `include_bytes!`
continue to be treated as data. The scanner is a conservative source gate with
no general macro expansion engine. The 35 Python scanner controls include lawful and negative cases through
default discovery in a temporary Git repository.

**B124-02.** The declaration token digest preserves literal tokens without
treating their contents as code. A changed ABI literal changes that digest. The
entry also binds the containing file's raw bytes, covering same-file outer
attributes and surrounding context. The aggregate keyword byte offset disambiguates identical spelling at
different locations. Each entry must match exactly one actual declaration and
every bounded declaration needs its own entry. The guard rejects repeated
actual matches and entries for macro templates or spliced source. The test suite covers ABI drift, ordinary declaration drift, same-file
context drift, duplicate declarations, and stale and duplicate entries. No
entry is authorized by the suite or by the Target A finding. Cross-file
context and expansion remain part of focused human review.

The five checked-in scanner fixtures cover generic and lifetime bounds,
where clauses, the protected array-unification declaration shape, and lawful
unbounded and const-parameter declarations.

### Compiler-status probe

**B124-03.** The driver checks the chosen rustc identity with `-vV`, runs a
known-good compile control, and records compile-only diagnostics and status.
An expected success must produce a fresh nonempty metadata file. A successful
negative observation requires a recognized lifetime or well-formedness error
at a relevant primary span in the particular source. The explicit-type
control must reject on both compiler paths. Fixed mode also requires a
classified rejection of the original control. Unknown diagnostics, ICEs,
signals, missing input and output failures are inconclusive or failures.
Nineteen mocked process controls exercise these cases without invoking Rust
locally. Fixed mode requires an explicitly selected release, full commit hash,
and host. The recorded rejection matcher checks E0597 at the exact borrow
site. A different diagnostic in a future release requires focused review.
The two checked-in control sources are unchanged, and only metadata is emitted.

### Continuous integration

The tests workflow runs the source guard, scanner and probe-driver controls,
and the compile-only probe for every push and pull request. The docs workflow independently verifies
that TC-001 remains in the generated AI context bundle. The checks apply before
any future N1 source can be accepted or merged.

## Maintenance and retirement

When upstream provides a candidate fixed release:

1. verify the upstream issue, repair, release notes, and exact compiler identity;
2. change the pinned toolchain only in a dedicated reviewed update;
3. invert the status probe from `affected` to `fixed`;
4. require the original and variant probes to fail compilation for the intended
   lifetime/WF reason rather than an unrelated host error;
5. run complete debug, release, Clippy, rustfmt, documentation, installation,
   native, and BED-specific gates applicable at that time;
6. reconcile any newly rejected code as a possible true positive before repair;
7. obtain independent review and Greg's explicit disposition;
8. retain the source guard unless that disposition expressly narrows or retires it.

No agent may infer retirement from a green compiler build, a changed diagnostic,
an upstream merge, a matching digest, or the absence of a current exploit.
